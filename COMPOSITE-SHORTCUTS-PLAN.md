## Plan: Composite Shortcuts

**TL;DR** — Add a shortcut type that has no device targets of its own; instead it references
multiple existing shortcuts and runs them in sequence (each with their own chain). Composites can
themselves be chained from and can reference other composites. Think "playlist of shortcuts."

Properties:
- `int Id` — PK, generated by the database
- `int ShortcutId` — FK back to the owning `Shortcut`
- `int ReferencedShortcutId` — FK to the referenced `Shortcut` (plain FK, no navigation property,

- `int DelaySeconds` — delay before running the referenced shortcut (0–60, validated in service)
- `int Order` — the position in the sequence (since referenced shortcuts run in order)

Rationale for including `Order`: the user picks shortcuts in a specific sequence; the DB must

Also update the XML doc on `Targets` to note the mutual exclusivity:

Inside `OnModelCreating`, add a new `modelBuilder.Entity<ShortcutReference>(...)` block after the
existing `ShortcutTarget` block:

```csharp
modelBuilder.Entity<ShortcutReference>(entity =>
{
    entity.HasKey(r => r.Id);
    entity.HasOne<Shortcut>()
        .WithMany(s => s.ReferencedShortcuts)
        .HasForeignKey(r => r.ShortcutId)
        .OnDelete(DeleteBehavior.Cascade);

    // Plain FK to the referenced shortcut — no navigation property (same style as
    // Shortcut.NextShortcutId). SetNull (not Cascade) so deleting a referenced shortcut just
    // breaks the link instead of deleting the composite that references it.

        .WithMany()
        .HasForeignKey(r => r.ReferencedShortcutId)
        .OnDelete(DeleteBehavior.SetNull);

    entity.Property(r => r.DelaySeconds).HasDefaultValue(0);
});
```

auto-discovers it via the `WithMany(s => s.ReferencedShortcuts)` call — no other changes to
the `Shortcut` entity configuration are needed.

### 3.1 `src/GoveeController.Application/Shortcuts/IShortcutService.cs`

Add two new methods:

```csharp
/// <summary>
/// Creates a composite shortcut that references other existing shortcuts instead of targeting
/// devices directly. Applying it runs each referenced shortcut in sequence (after its configured
/// delay), with each referenced shortcut's own chain running in full. Composite shortcuts can
/// themselves be referenced by other composites (subject to cycle detection) and can have their
/// own <see cref="Shortcut.NextShortcutId"/> chain link. At least one referenced shortcut is
/// required. Mutually exclusive with device-targeted shortcuts — a shortcut is either composite
/// or device-targeted, never both.
/// </summary>
Task<Shortcut> CreateCompositeShortcutAsync(
    string name,
    IReadOnlyList<(int ReferencedShortcutId, int DelaySeconds)> referencedShortcuts,
    int? nextShortcutId,
    int nextShortcutDelaySeconds,
    CancellationToken cancellationToken = default);

/// <summary>Overwrites an existing composite shortcut. Same rules as
/// <see cref="CreateCompositeShortcutAsync"/>.</summary>
Task UpdateCompositeShortcutAsync(
    int id,
    string name,
    IReadOnlyList<(int ReferencedShortcutId, int DelaySeconds)> referencedShortcuts,
    int? nextShortcutId,
    int nextShortcutDelaySeconds,
    CancellationToken cancellationToken = default);
```

Also add to the interface:

```csharp
/// <summary>
/// Lists shortcuts that may legally be referenced by the composite shortcut identified by

/// shortcuts that would create cycles (including indirect cycles through chains).
/// </summary>

    int? forShortcutId, CancellationToken cancellationToken = default);
```

### 3.2–3.3 `src/GoveeController.Application/Shortcuts/ShortcutService.cs`

**`CreateCompositeShortcutAsync`:**

1. Validate `referencedShortcuts` is non-empty
2. Validate each delay is 0–60
3. Load all shortcuts, resolve to dictionary
4. Validate each referenced shortcut exists
5. Validate no self-reference (`referencedShortcutId != currentId` — currentId is null for create,
   but keep the check for update)
6. Validate no cycles: for each referenced shortcut, walk its full downstream (its
   `NextShortcutId` chain AND its own `ReferencedShortcuts`, recursively) and ensure none reach
   `forShortcutId` (null for create, so this only matters for update)
7. Validate the `NextShortcutId` chain link using existing `ValidateChainLink`
8. Build the `Shortcut` with empty `Targets`, populated `ReferencedShortcuts` (with `Order` set
   from the list index), and `PowerOn`/`Brightness`/`Color*` left at defaults (they are
   meaningless for composites)
9. Persist via `_repository.AddAsync`

**Cycle validation helper** — extract a private method (used by both create and update):

```csharp
/// <summary>
/// Returns true if walking the full downstream of <paramref name="startId"/> (its
/// NextShortcutId chain AND the chains of any shortcuts it references) ever reaches
/// <paramref name="targetId"/>. Used to prevent composites from creating indirect cycles.
/// </summary>
private static bool DownstreamContains(
    Dictionary<int, Shortcut> byId, int startId, int targetId, int maxDepth = 10)
```

Walk algorithm:
- Start at `startId`, visit its `NextShortcutId` chain (using the existing `WalkChainLength`
  pattern) — if any node's ID equals `targetId`, return true
- For each node visited (including `startId`), also walk each of its `ReferencedShortcuts`:
  for each referenced shortcut's ID, recurse into `DownstreamContains`
- Use a `HashSet<int>` of visited IDs to prevent infinite recursion from unexpected cycles
- Cap total depth at 10 (defensive — composites referencing composites referencing composites…)

**`UpdateCompositeShortcutAsync`:** Same validation as create, plus the `currentId` parameter
for cycle detection. Clear-and-re-add handled by repository (already updated in Phase 2).

### 3.4 `ApplyShortcutAsync` — handle composites

The current `ApplyShortcutAsync` resolves the `NextShortcutId` chain into a `List<Shortcut>`,
then iterates each step applying its `Targets`. Update this to handle composite steps.

Replace the inner per-step loop so that for each step in the chain:

1. If the step has `Targets` (non-empty): apply them as today (existing `ApplyToTargetAsync` loop)
2. If the step has `ReferencedShortcuts` (non-empty): for each reference in `Order`:
   a. Look up the referenced shortcut from `byId`
   b. Apply it via the same logic — but instead of duplicating, **extract the per-target
      application logic into a private `ApplyOneStepAsync(Shortcut, byId, failures, ref
      succeededCount, ref totalCount, ct)` method** that dispatches to targets or referenced
      shortcuts as appropriate
   c. Wait the reference's `DelaySeconds` before the next referenced shortcut
3. After all referenced shortcuts (or targets) for this step, wait the step's
   `NextShortcutDelaySeconds` before the next chain step (existing behavior)

The `ApplyOneStepAsync` method handles the recursion: when a composite references another
composite, that referenced composite's `ApplyOneStepAsync` will in turn iterate its own
`ReferencedShortcuts`. This naturally handles arbitrary nesting.

**Important:** increment `totalCount` by the number of referenced shortcuts (not device targets)
for composite steps, so the `ShortcutApplyException` message ("applied to N of M shortcuts")
makes sense.

**Defensive recursion cap:** Add a `HashSet<int> visitedShortcutIds` parameter to
`ApplyOneStepAsync` to prevent infinite recursion if a corrupted database creates a reference
cycle. Skip any shortcut already in the set (and log a warning).

### 3.5 `ListEligibleReferencedShortcutsAsync`

Similar pattern to `ListEligibleNextShortcutsAsync` but checks: no self-reference, no cycles
(using `DownstreamContains`), shortcut exists.

## Decisions *(settled — do not relitigate)*

| Question | Decision | Rationale |
|---|---|---|
| Separate service methods vs. overloaded? | **Separate methods** (`CreateCompositeShortcutAsync`, `UpdateCompositeShortcutAsync`) | Keeps the existing device-target API clean. Composites have fundamentally different parameters (no power/brightness/color). Overloading would create confusing "some params are ignored" semantics. |
| How are referenced shortcuts ordered? | **`Order` column on `ShortcutReference`** | Insertion order is not reliably preserved by EF Core. An explicit order column is unambiguous and supports future reordering UI. |
| Can composites reference other composites? | **Yes**, with cycle detection | The user confirmed this. The `DownstreamContains` check prevents cycles including indirect ones through chains. |
| Do referenced shortcuts count toward the 3-shortcut chain cap? | **No** — the chain cap only applies to the linear `NextShortcutId` chain | Referenced shortcuts are a different dimension. Enforcing the cap across referenced shortcuts would make composites nearly useless with the current cap of 3. If rate-limiting concern arises, the per-reference delay is the mitigation. |
| What happens to `PowerOn`/`Brightness`/`Color*` on composites? | **Left at defaults** (PowerOn=false, everything null) | These fields are meaningless for composites. They already exist on the `Shortcut` entity and we don't remove them — just don't populate them. The UI hides these fields for composites. |
| Delete behavior when a referenced shortcut is deleted? | **SetNull** on `ReferencedShortcutId` (same as `NextShortcutId`) | Breaks the link cleanly without deleting the composite. The composite shows "missing shortcut" or skips it during apply. |
| Recursion depth for composite references? | **Defensive cap of 10** | Prevents infinite loops from corrupted data. In practice, references will be 1–2 levels deep. |

## Scope Boundaries

**In scope:**
- `ShortcutReference` entity and EF Core configuration
- `CreateCompositeShortcutAsync` / `UpdateCompositeShortcutAsync` service methods
- Cycle detection for referenced shortcuts (including indirect cycles through chains)
- `ApplyShortcutAsync` changes to handle composite steps recursively
- UI toggle between device and composite shortcut modes
- Referenced shortcut picker with add/remove/reorder and per-reference delay
- Composite shortcuts appear distinctly in the list (badge + referenced shortcut names)
- `ListEligibleReferencedShortcutsAsync` for dropdown population
- Tests for the service-layer methods (Phase 5)

**Deliberately excluded:**
- **Bulk editing referenced shortcuts** (adding 10 at once) — the UI supports one-at-a-time
  add/remove. Bulk is a separate feature.
- **Drag-and-drop reordering** — up/down buttons are simpler and sufficient for the typical
  2–5 referenced shortcuts. Drag-and-drop requires JS interop.
- **Nested composite preview in the list** — the list shows "references: Movie Mode, Dim Lights"
  but does not expand to show Movie Mode's own references. That's what the expanded details are
  for; nesting in the list would be noisy.
- **bUnit component tests** — same reasoning as the improvement plan §4.5. Optional follow-up.
